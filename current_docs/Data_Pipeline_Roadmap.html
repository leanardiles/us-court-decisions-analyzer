Data Pipeline Roadmap

How we get from 541 Word opinions to a frozen 20-case pilot, then Postgres + pgvector — without rebuilding the app.

Court Opinions Analyzer, Phase II · Improving Reliability in Legal AI Through Multi-Agent Verification
Prepared by Enock Katenda (Infrastructure) · For Alex Ji, Leandro Ardiles, Tafadzwa Nyemba
30 September 2026

1. Why this document exists

Capstone II is an experiment: keep the Capstone I application as System A, add a multi-agent layer as System B, and measure whether agent disagreement catches bad legal answers better than self-reported confidence.

The real corpus is not currently in the app. It lives as 541 LEXIS Word files. The app today only uploads Parquet into SQLite. The later Evidence Checker will need cited spans, which means chunked text with offsets — and eventually pgvector.

Decision: we do not start a new repository or a new product. The pipeline is added inside us-court-decisions-analyzer. It feeds the existing upload / module-launch / validator workflow. Postgres and pgvector come after a usable 20-case set exists, not before.

Stage 0 — Frozen pilot (this week) Done

Goal. Unblock the 7 October benchmark without waiting for Postgres.

How it runs. A CLI walks current_docs/MS Word files (544 files total)/, extracts text, hashes files, groups duplicates, and writes a Parquet file whose columns already match the existing upload parser.

Command (from backend/): python -m app.ingest.cli --pilot 20

Result of the first run (30 Sep 2026). 541 files parsed, 0 failures, 540 unique opinions, 77 same-name alias groups (e.g. Veasey v. Perry (2)). Twenty unique cases selected with a length cap so they fit in an LLM context window (about 2k–48k characters of opinion text). All 20 have a parsed date; 17 have a docket number.

Still required from the team: Tafadzwa reviews the 20 names for Q1/Q2 suitability and writes the answer key. After that review, the manifest is frozen. If a case is a bad fit, we swap it in a new manifest version — we do not silently regenerate the list.

Stage 1 — Word → structured cases Next

Goal. Reliable metadata and opinion / dissent / concurrence splits for the whole corpus, still as a CLI. No new UI. No embeddings.

How it runs.

  1. Extract paragraphs with python-docx / XML (already working).
  2. Strip remaining LEXIS artifacts (reporter stars, counsel blocks, “End of Document”).
  3. Parse caption fields with rules first: case name, court, date, citation, docket, judges. Use an LLM only if rules fail — do not spend Groq budget on 541 files.
  4. Split body into opinion / dissent / concurrence.
  5. Dedup by text hash; keep filename aliases as sources, not extra cases.
  6. Write one canonical row per unique opinion. Leave election_type empty. Humans and agents answer Q1; ingest must not invent it.

Success. Unique opinions load (~450 after alias collapse). A parse-failure report exists. Docket / court / date quality is good enough for the experiment log.

When. 1–8 October, in parallel with the model benchmark.

Stage 2 — Move storage to Postgres Weeks 3–4

Goal. Same 13-table workflow, now on Postgres, so pgvector can be added later. SQLite remains a Dummy-AI fallback.

How it runs.

  1. Docker Compose: Postgres 16 + CREATE EXTENSION vector;
  2. Point DATABASE_URL at Postgres. Add Alembic (already planned in the schema changelog).
  3. Port existing tables unchanged. Do not redesign court_cases or launch_module().
  4. Add only ingest columns: source_documents (path, sha256, parse status) and on court_cases: source id, citation, raw text, character length.

Success. Login, project, module, validator, and feedback flows still work. Official experiments can load the frozen 20 from Postgres instead of a one-off Parquet upload.

Stage 3 — Chunking + pgvector After Stage 1 is clean

Goal. Store opinion pieces with stable character offsets so an agent can cite a span and an Evidence Checker can verify it.

How it runs.

  1. Split on legal sections first (Opinion, Dissent, I., II.), then paragraphs, then 400–800 token windows with overlap.
  2. Save char_start / char_end against the cleaned source text. Round-trip test: raw_text[start:end] == chunk.text.
  3. Embed with a local/open model (e.g. nomic-embed-text). Do not spend the Groq experiment budget on embeddings.
  4. Write opinion_chunks (vector column) and ingest_runs (files seen, cases written, errors).

What this is not. Not a chatbot. Not a replacement for sending the full opinion on the 20-case pilot. Readers still get the whole opinion for Q1/Q2. Retrieval is for long documents, span citation, and Phase 5 evidence checking.

When. Once Stage 1 metadata is trusted; target late October so it is ready before the Evidence Checker.

6. What we will not do

  • Do not create a second GitHub project or a chatbot UI.
  • Do not embed before metadata parse and dedup are trusted. Garbage vectors are expensive to redo.
  • Do not send 541 full opinions through Groq to “extract everything.” Rules for captions; Groq budget is for the 20-case benchmark.
  • Do not invent a new case schema that breaks launch_module(). Add columns; do not fork CourtCase.
  • Do not treat filename as identity. Use content hash + parsed caption. Copies like (2).docx are aliases.
